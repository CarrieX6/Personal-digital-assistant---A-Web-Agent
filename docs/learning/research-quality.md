# 调研证据、完整性审查与文档维护方法

作者：**Zhuofan Xie**  
更新日期：2026-07-28  
成熟度：方法已建立，平台和项目实验需持续补充  
关联任务：`LEARN-001`、`LEARN-RESEARCH-001`

本文用于判断一篇文档是否“调研充分”。链接数量多不等于证据充分；官方文档说明
“能做什么”，项目实验才说明“在本项目约束下是否值得做”。

## 1. 四种陈述必须分开

| 标签 | 含义 | 可以支持什么 |
| --- | --- | --- |
| 官方/标准事实 | 标准、平台或框架明确说明的行为 | 能力、协议、限制、版本 |
| 论文结论 | 原始论文在其数据和设置下报告的结果 | 方法原理和已报告实验，不自动代表本项目 |
| 工程推断 | 根据事实和项目约束推导的建议 | 候选方案和实验设计 |
| 项目证据 | 本项目代码、测试、真机或账号实验 | 项目适用性、性能和验收 |
| 项目决策 | 已记录权衡、批准并生效的 ADR | 实现方向 |

文档应使用“官方说明”“项目建议”“待实验”“ADR 已决定”等明确措辞，不能把工程
推断写成平台承诺，也不能把框架提供某功能写成当前代码已经具备。

## 2. 来源优先级

1. 标准正文、监管/平台官方文档；
2. 框架官方版本文档、迁移指南、官方仓库和 release；
3. 原始论文、模型卡、数据集说明和许可证；
4. 项目可复现源码、测试与实验原始记录；
5. 高质量二手资料只用于发现线索或补充解释。

博客、排行榜、Star 数和厂商宣传 Demo 不能单独支撑架构决策。动态能力、价格、配额、
许可和平台审核规则必须标注核对日期。

## 3. 一项调研何时算充分

至少回答：

- 问题、用户链路和不做什么是否明确；
- 候选是否覆盖“自研/简单方案”和主流可用方案；
- 每个候选的能力、代价、失败模式、许可和退出路径是否有证据；
- 哪些结论来自文档，哪些必须通过账号、设备或基准实验；
- 是否使用同一输入、指标和环境公平比较；
- 是否记录失败结果和不确定性；
- 是否形成 ADR，或说明当前为什么不需要决策；
- 哪些上游变化会触发重新审查。

只有官方文档而没有项目实验时，成熟度最多是“已核对/待实验”；不能标记“已验证”。

## 4. 当前知识库覆盖审查

审查日期：**2026-07-28**。

| 分域 | 架构清晰度 | 知识覆盖 | 证据状态 | 当前主要缺口 |
| --- | --- | --- | --- | --- |
| 工程基础 | 清晰 | Web、异步、可靠性、数据、LLM、安全较全 | 官方标准/文档已覆盖 | 原缺项目环境与调试主线，本轮已补 |
| Web Agent | 清晰 | Loop、架构、调度、Memory、框架、协议、评测较全 | 框架官方资料较充分 | 框架横评、真实 Provider 和恢复实验未做 |
| 外部控制 | 清晰 | Gateway、飞书、微信路径、部署、预览较全 | 飞书资料较强 | 微信只有官方入口级证据；真实主体/账号 PoC 未做 |
| 身份安全 | 原先偏散 | 风险和 Policy 较全 | OWASP/NIST 已覆盖 | 原缺 OAuth/OIDC/PKCE 的实现边界，本轮已补 |
| 移动端 | 基本清晰 | 后台限制和部署拓扑已覆盖 | iOS/Android 官方资料较充分 | HarmonyOS 仅部分覆盖，需版本化真机矩阵 |
| 产品化 | 清晰 | Capability、供应链、数据、性能、运维、UX 较全 | 标准和官方资料较充分 | 尚无项目性能、安全和恢复基线 |
| AI 功能/模型 | 只有大纲 | 范围完整但没有正文 | 未调研 | 按当前计划暂缓，不应误标为已覆盖 |

因此当前文档适合建立完整心智模型，但在本轮新增实战路线之前，不够适合作为“从零
照做”的教程；框架、渠道、移动端和性能部分仍需实验，不能称为最终选型报告。

## 5. 本轮时效性核验

- MCP 当前正式规范修订为 `2025-11-25`，新增文档应固定 revision，不使用无版本
  链接暗示永久稳定
  （[MCP Specification 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25)）。
- Android NNAPI 已在 Android 15 弃用；官方迁移指南建议转向可更新的 TensorFlow
  Lite/LiteRT 路径，并可按场景使用 GPU delegate
  （[Android NNAPI Migration Guide](https://developer.android.com/ndk/guides/neuralnetworks/migration-guide)）。
- OAuth 安全实践应以 2025 年发布的 RFC 9700 为当前 BCP，并结合原生应用 RFC 8252
  和 PKCE，而不是只引用早期 OAuth 2.0 基础 RFC
  （[RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html),
  [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.html)）。

## 6. 已知证据不足项

### 微信生态

现有正文足以确定“个人微信无通用公开 Bot API，不采用非公开协议”的项目边界，但
企业微信、公众号和小程序尚未逐项记录主体要求、消息窗口、媒体限制、回调重试与
审核规则。`CHANNEL-003` 必须建立平台能力矩阵并做真实账号 PoC。

### HarmonyOS

现有正文只用 Push Kit 支撑“使用官方推送通道”的原则，没有完成特定 HarmonyOS
版本的后台任务、Deep Link、WebView/WebGL 和端侧推理证据。当前结论只能标为
“部分核对，真机待测”。

### 框架选型

官方文档可以确认 LangGraph、Pydantic AI、ADK、Microsoft Agent Framework 等提供
哪些抽象，不能证明哪个更适合本项目。`AGENT-001` 必须使用同一任务、故障注入和
维护成本口径横评。

### Provider 与模型

预置 Base URL 和模型名是应用配置，不是可用性保证。供应商目录、视觉输入、Tool
Calling、上下文、价格和数据策略会变化；`LLM-001` 应在指定区域、账号和日期下做
连接测试并保存原始结果。此项不在本轮扩写路线 E。

## 7. 更新触发器

出现以下任一变化时，把相关文档标为 `需更新`：

- 标准发布新 revision；
- 框架 major/minor 改变关键 API 或维护状态；
- 平台权限、回调、媒体、审核或主体规则变化；
- 模型、价格、上下文、许可或数据策略变化；
- 操作系统弃用 API 或改变后台策略；
- 项目目标、目标设备、安全边界或用户规模变化；
- 实验结果否定了文档中的工程推断。

建议动态主题每三个月检查一次；进入实现前必须再核对一次，不以定期检查替代实现前
核验。

## 8. 文档审查清单

- [ ] 作者、日期、成熟度和任务 ID；
- [ ] 结论与证据逐项对应；
- [ ] 版本、平台、区域、账号类型和设备范围明确；
- [ ] 主要候选、简单基线和不采用方案均有理由；
- [ ] 优缺点包含失败、迁移、许可、安全和运维；
- [ ] 动态信息有核对日期；
- [ ] 不确定项进入实验或看板；
- [ ] 决策进入 ADR；
- [ ] 本地链接无断链；
- [ ] 路线 E 的状态没有被正文数量虚高。
