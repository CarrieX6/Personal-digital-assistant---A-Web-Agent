# Token 用量、预算与节省策略

作者：**Zhuofan Xie**
更新日期：2026-09-28

## 1. 为什么需要单独的 Token 架构

Agent 的成本和稳定性不能只靠 Prompt 约束。一次 Run 可能经历首轮规划、工具结果
续规划、最终回答，以及会话压缩摘要；如果供应商重试、模型返回过长工具参数或用户
重复点击，就可能在目标已经完成后继续消耗 Token。因此项目把 Token 当成一次 Run 的
可观测资源，与步骤、权限、幂等键一样由代码控制。

这不是把 Token 写入用户记忆。系统只保存计数、阶段、模型、耗时和“真实/估算”标记，
不保存 Prompt、图片 base64、工具结果正文或 API Key。

## 2. 当前实现

### 2.1 供应商边界记录

`OpenAICompatiblePlanner._chat()` 是所有 Chat Completions 请求的统一边界：

1. 先执行已有的上下文窗口硬门禁，计算序列化输入上界、图片视觉 Token 保留和输出上限；
2. 请求前检查可选的 `AGENT_RUN_TOKEN_BUDGET`，预计超预算则不发 HTTP 请求；
3. 请求成功后解析 OpenAI 常见的 `prompt_tokens / completion_tokens / total_tokens`，
   同时兼容 `input_tokens / output_tokens`；
4. 供应商没有返回 `usage` 时，使用本地 Tokenizer/保守 JSON 估算，并标记
   `is_estimate=true`，不能把估算值冒充账单真实值；
5. 将事件写入 `token_usage.sqlite3`，按 `owner_id + run_id + thread_id + stage`
   关联，SQLite 文件权限为仅当前用户可读写。

阶段目前包括：`context`（会话摘要）、`plan`（首轮规划）、`decide`（工具结果后的
续规划）和 `final`（最终回答）。Web Run 响应和 `GET /api/usage/tokens` 都会返回
不含内容的汇总，便于控制台显示和后续计费/报表接入。

### 2.2 Run 预算门禁

默认不强行限制，保持已有部署兼容。设置环境变量后启用：

```bash
export AGENT_RUN_TOKEN_BUDGET=65536
```

门禁以“本次请求输入保守上界 + 输出上限”预估，累计到同一个 Run。超限直接返回安全错误，
不会继续重试或执行下一工具。它是防失控的硬上限，不是供应商账单精确计费；精确账单仍
以供应商返回的 `usage` 为准。

## 3. 与上下文压缩的配合

项目已有 `ContextBuilder`，按固定预算组合系统策略、当前消息、最近历史、会话摘要、
长期记忆、附件元数据和筛选后的工具 Schema。节省 Token 的顺序应保持如下：

1. **先限工具集合**：根据意图只发送本轮可能使用的工具，不把全部 Schema 每轮重复发送；
2. **再去重记忆**：当前消息或最近历史已出现的记忆不重复注入；
3. **压缩旧历史**：保留最近可操作消息，把更早内容变成有来源的结构化摘要；
4. **限制工具输出**：工具返回摘要、ID、状态和必要错误，原图、二进制和大段日志留在资产
   或任务存储中；
5. **最后截断**：仍超预算时优先截断低价值历史，保留当前用户消息和最终约束。

图片不要把 base64 持久化到 Checkpoint 或会话历史。视觉请求只在当前调用瞬时注入，
工具侧保存 `asset_id` 和受控预览 URL。

## 4. 下一阶段的节省与成本工程

| 优化 | 实施方式 | 关注指标 |
| --- | --- | --- |
| 意图/路由小模型 | 规则优先，低风险分类使用本地小模型；复杂规划才用大模型 | 路由准确率、每 Run 总 Token |
| 工具 Schema 缓存 | 对稳定版本做本地序列化缓存，运行时只发送选中的差异 | Schema Token、首条延迟 |
| 结果摘要 | 每个 Tool 定义最大结果字节和字段白名单；大结果存资产 | 工具结果 Token、信息损失率 |
| 模型分层 | 摘要/改写用便宜模型，视觉和复杂决策按能力路由 | 成功率、成本/Run |
| 请求去重 | 前端同步锁 + `Idempotency-Key`；相同任务不重复规划和推理 | 重复 Run 数、节省 Token |
| 缓存与复用 | 对确定性只读查询、相同图片指纹和相同参数复用结果 | 命中率、节省 Token |
| 输出限制 | 每个阶段单独设置 `max_tokens`，最终回答默认短格式 | P95 输出 Token、用户满意度 |
| 并发预算 | 多用户按 owner/任务队列限制同时运行的模型数和显存 | 排队时延、失败率、峰值显存 |

不建议为了省 Token 把所有历史永久压成一句话，也不建议把所有步骤交给一个大模型；
应使用基准任务集比较“成功率下降”与“Token 减少”的 Pareto 边界。

## 5. 验收与告警

最低验收项：

- 每个真实模型请求都有一条事件，且没有 Prompt/图片正文；
- 有 `usage` 时显示真实计数，无 `usage` 时明确显示估算；
- 预算耗尽时 HTTP 不出站、工具不执行、Run 进入稳定失败；
- 同一 Run 的 `plan → decide → final` 事件可按时间排序；
- 多 owner 查询不会读到其他 owner 的事件；
- 监控至少记录每日总 Token、P50/P95 每 Run Token、估算占比、预算拒绝数、重试率和
  单工具平均 Token。

生产环境还需要维护供应商价格版本表，把 Token 计数映射为费用；在没有价格和币种版本
之前，只能报告 Token，不能声称“节省了多少元”。
