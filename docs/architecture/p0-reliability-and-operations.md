# P0 可靠性与运维基线

更新时间：2026-09-28
适用范围：本地单机节点、Web 控制台、飞书长连接、空间照片与图片风格化任务。

> 2026-10-08 入口范围复核：原子预留/claim 是服务层能力，不代表所有 HTTP 路径都传入幂等键。
> 当前图片风格化直接 API 读取 Idempotency-Key，空间照片 Agent/飞书路径传入执行/消息键，
> 但直接 POST /api/spatial-scenes 未转发该请求头；不可据此宣称所有入口都实现跨进程防重。
> 工具执行账本与图像 Job 原子 claim 也是两种机制，不能推断通用 exactly-once。
> 实操和代码入口见[扩展、测试与上线门槛](../handbook/07-extension-and-operations.md)。

本文记录当前 P0 的工程边界。它不是“已经达到生产级”的声明，而是让新设备迁移、重启、重复点击和外部渠道抖动时，系统仍能给出可解释状态，并把尚未完成的生产化工作显式留下。

## 1. 任务幂等与多进程安全

任务创建采用两阶段：先在 SQLite 中以事务原子预留 `assets` 和 `jobs`，再写入源图片文件并提交到执行器。带 `Idempotency-Key` 的请求使用 owner、功能和 key 生成稳定 UUID；同一个 key 的第二次请求只读取已有资产，不会再创建任务。若同一个 key 携带不同图片或参数，系统拒绝请求，避免静默覆盖。

执行前通过 `claim_job(job_id, worker_id)` 的条件更新将 `queued` 变为 `running`。条件更新成功的进程才可以执行；其他进程直接返回已有任务。运行中记录 `worker_id`、`lease_until` 和 `attempt_count`，阶段进度刷新租约。这样即使 Web 进程和后台恢复进程同时扫描队列，也只有一个执行者。

服务启动时只回收租约已过期（或旧版本没有租约）的 running 任务；未开始的 queued 任务自动重新提交。被回收的任务进入 `failed/interrupted`，保留原始资产，可由用户一键重试。当前重试采用原子 `failed → queued`，尚未引入指数退避和死信队列。

## 2. 失败重试与可恢复边界

- 空间照片和图片风格化均复用已保存的清洗源图，不要求用户重新上传。
- 飞书入站消息以 `message_id` 去重；空间照片任务额外使用 `feishu:chat:sender:message` 幂等键。
- 飞书图片下载按 IM 消息资源、图片资源和 channel-level downloader 顺序尝试，每条路线最多短重试两次；出站文本、Markdown、图片、文件和卡片使用稳定 UUID 做三次短重试。
- 当前仍缺少通用持久化 Outbox、指数退避、死信队列、取消信号和跨节点队列；这些不能被本地 ThreadPoolExecutor 冒充完成。

## 3. 结构化日志、健康检查和指标

当 `AGENT_LOG_FORMAT=json` 时，后端输出包含时间、级别、logger、消息和异常的 JSON 日志。
指标注册表不采集 prompt、图片内容或凭证，但 `JsonLogFormatter` 会保留调用点的消息和异常，
不提供通用自动脱敏；不能保证任意新日志都不含敏感正文。共享日志前需核对内容，生产采集需
加入过滤、访问控制与保留策略。默认本地开发仍保持原有文本日志。

- `GET /health`：能力概览，兼容原有控制台。
- `GET /ready`：API、LLM 配置和资产数据库就绪性；飞书是可选渠道，不会阻塞本地 Web 使用。
- `GET /api/ops/metrics`：仅允许本机 root 访问，返回 HTTP 请求计数/耗时、任务状态计数、飞书状态和 Token 用量汇总。

当前指标是进程内聚合指标，适合本机验收与迁移排障；生产部署还需要 Prometheus/OpenTelemetry 导出、按功能/状态/错误类型分层、持久化历史、告警规则和脱敏日志采集。

## 4. P0 验收建议

1. 同一消息快速连续点击两次：资产和 job 数量只能增加一次。
2. 两个进程同时打开同一资产数据库：只能有一个 `claim_job` 成功。
3. 服务在 queued 状态重启：任务自动恢复；在 running 状态且租约过期重启：任务标记中断并可重试。
4. 飞书图片资源主 API 不可用时：fallback downloader 能够完成下载；权限错误返回平台错误码和“消息资源/媒体下载权限”提示。
5. 让出站 channel 第一次返回瞬时错误：同一 UUID 重试，用户最多看到一条成功消息。
6. 查看 `/ready` 与 `/api/ops/metrics`，确认无需读取用户正文即可定位队列堆积、5xx 和 Feishu 连接问题。

## 5. 下一阶段生产化

P0 完成后仍需把执行器替换为持久化任务队列（SQLite 单机版可先做 DB poller，生产再选 Redis/RQ、Celery、Dramatiq 或云队列），增加指数退避与死信；引入 Outbox 记录渠道发送状态；增加模型/工具耗时、成功率、显存和费用指标；并通过真实 macOS/Windows/NVIDIA、断网、休眠、进程崩溃和多用户并发压测验收。
