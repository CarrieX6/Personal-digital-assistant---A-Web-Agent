# 空间照片与飞书链路性能基线（2026-09-03）

作者：**Zhuofan Xie**

- 实验 ID：`PERF-EXP-001`
- 关联任务：`PERF-001`、`SPATIAL-001`、`CHANNEL-001`
- 结论等级：本机可重复的工程基线，不是生产 SLA

## 1. 实验目的

回答当前阶段最重要的四个性能问题：

1. 空间照片单图平均、P95、冷启动和热启动耗时；
2. 生成过程的峰值内存与 Metal 资源占用；
3. 飞书消息进入本机后，多久能收到确认和最终结果；
4. 当前瓶颈在模型推理还是分层、补全与编码。

## 2. 环境与口径

| 项目 | 配置 |
| --- | --- |
| 设备 | Apple M4，10 核 CPU / 10 核 GPU，16 GB 统一内存 |
| 系统 | macOS 15.6 |
| 深度模型 | `Depth Anything V2 Small`，本地缓存、离线加载 |
| 主体分割 | `auto`：Apple Vision → BiRefNet → 深度蒙版降级 |
| 输入集 | 9 张不同图片，最长边 1120–1600 像素 |
| 生成样本 | 20 次，`max_workers=1` |
| 运行时 | Python 3.9、PyTorch 2.8、Transformers 4.57.6 |

项目 `.venv` 的 Python 3.12 / PyTorch 2.13 在本机导入阶段超过 384.62 秒仍未完成，
因此本次使用已可用的系统推理环境完成基线。这个现象属于部署冷启动缺陷，后续必须在
项目标准环境中复测，不能把本记录直接作为发布承诺。

内存口径为进程峰值 RSS。Apple Silicon 使用统一内存，MPS 的 `driver allocated` 与 RSS
可能重叠，二者不能相加当作总内存。

## 3. 空间照片结果

### 3.1 端到端耗时与成功率

| 指标 | 结果 |
| --- | ---: |
| 成功生成率 | 20/20（100%） |
| 全部 20 次平均耗时 | 5.030 s |
| 全部 20 次 P95 | 7.584 s |
| 热启动 19 次平均耗时 | 4.783 s |
| 热启动中位数 | 4.463 s |
| 热启动 P95 | 7.408 s |
| 热启动最小 / 最大 | 3.896 s / 7.472 s |
| 首次冷启动生成 | 9.719 s |
| 进程启动至首次完成 | 9.872 s |

在同一张风景图上的热启动平均为 7.437 秒，相比首次 9.719 秒下降 23.5%。20/20 只说明
这组受控样本没有失败，不能替代更大图片集、异常输入、并发和长时间运行的成功率验证。

### 3.2 热启动阶段拆分

| 阶段 | 平均耗时 | P95 | 热启动总耗时占比 |
| --- | ---: | ---: | ---: |
| 提交、解码、缩放、WebP 与数据库 | 0.193 s | — | 4.0% |
| Worker 准备 | 0.018 s | 0.031 s | 0.4% |
| 深度估计 | 0.252 s | 0.315 s | 5.3% |
| 主体分割 | 0.443 s | 0.538 s | 9.3% |
| 分层、遮挡补全与 WebP 编码 | 3.860 s | 6.240 s | 80.7% |
| 资产打包 | 0.0075 s | 0.010 s | 0.2% |

当前首要瓶颈不是 `Depth Anything V2 Small`，而是 CPU 上的图层构造、遮挡补全和图片
编码。下一轮优化应优先拆分这三个子阶段，并比较矢量化、减少重复编码、分辨率分级和
GPU/Core Image 加速，而不是先更换深度模型。

### 3.3 资源占用

| 指标 | 结果 |
| --- | ---: |
| 进程峰值 RSS | 697.52 MiB |
| MPS current allocated | 232.76 MiB |
| MPS driver allocated | 1.275 GiB |

本轮未采集整机功耗、温度、任务完成后的内存回收曲线，也没有 NVIDIA 显存结果。它们仍是
`PERF-001` 的后续工作。

### 3.4 历史任务对照

资产数据库中保留的 10 个空间任务最终状态均为完成：全量平均 201.228 秒、P95
977.446 秒，其中两次出现 924 秒和 1021 秒的运行中断或调度停滞。去除大于 120 秒的
异常任务后，8 次平均 8.383 秒、P95 13.223 秒。

数据库只保留最终状态，重试可能覆盖尝试次数，因此该结果只能用于发现“历史运行存在长尾
停滞”，不能据此宣称历史成功率为 100%。需要通用 Job 事件账本后再测真实重试率和失败率。

## 4. 飞书到 Web / 结果回传基线

### 4.1 实际事件记录

| 指标 | 样本 | 结果 |
| --- | ---: | ---: |
| 飞书入站写入至首条出站记录平均 | 23 | 939.2 ms |
| 同上中位数 | 23 | 918.6 ms |
| 同上 P95 | 23 | 1191.1 ms |
| 空间任务早期确认平均 | 2 | 0.904 s |
| 空间任务创建平均 | 2 | 3.104 s |
| 结果图片记录平均 | 2 | 14.561 s |
| 最终 Viewer 卡片平均 | 2 | 15.675 s |

早期确认让用户约 0.904 秒看到“任务已接收”，如果等待最终 Viewer 才首次回复则约
15.675 秒；在这两条同源流程上，感知等待下降约 94.2%。这是基于现有事件时间戳的
反事实比较，并非独立版本 A/B 实验。

### 4.2 本地消息存储与 Web 可见性

| 指标 | 样本 | 结果 |
| --- | ---: | ---: |
| `channel_events` SQLite 单次写入平均 | 1000 | 1.408 ms |
| 写入 P95 | 1000 | 2.849 ms |
| 查询 200 条并 JSON 序列化平均 | 1000 | 0.381 ms |
| 查询 P95 | 1000 | 0.435 ms |

Web 控制台当前每 3 秒轮询一次。由轮询周期推算，消息持久化后被页面发现的平均额外等待约
1.5 秒、P95 约 2.85 秒、上限约 3 秒。这是理论值，不是“手机发送到 DOM 渲染”的真机
测量。后续应使用 SSE/WebSocket 事件推送替代高频轮询，并补浏览器 Performance 时间戳。

## 5. 当前判断与下一轮实验

1. 当前设备热启动单图约 4.8 秒，已经能支持异步交互，但 P95 7.4 秒和历史极端长尾仍需
   优化与监控；
2. 分层、补全和编码占热启动耗时约 81%，是优先性能目标；
3. 飞书早期确认有效改善感知等待，但最终回传仍依赖任务可靠性、Outbox 和公网 Viewer；
4. 下一轮至少使用 50–100 张分层测试集，在标准 `.venv`、Windows NVIDIA 和 CPU-only
   三种设备上重复冷/热启动、并发、失败恢复、功耗和内存回收测试；
5. 为每个 Job 写入不可覆盖的状态事件，才能准确计算成功率、重试率、取消率和长尾来源。
